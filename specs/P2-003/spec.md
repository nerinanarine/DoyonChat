# Feature Specification: APIエラー時のユーザーフレンドリーな表示

**Feature Branch**: `[feat/p1-003-p2-003-p2-013]`

**Created**: 2026-08-31

**Status**: Implemented（安全なErrorCode・SSE error event・再試行・ログアウト遷移を実装）

**Input**: [P2-003 backlog item](../000_backlog/items/P2-003-error-ux.md)

> **責務:** 本仕様は、BackendからFrontendへ安全に伝えるエラー契約と、FrontendでのAPIエラーの分類・表示・再試行を対象とする。ローディング中の表示状態はP2-013、ストリーミング停止時の中間保存はP1-003で扱う。

## User Scenarios & Testing

### User Story 1 - エラーの種類を理解する (Priority: P2)

ユーザーはAPIエラーが発生したとき、原因に応じた分かりやすい日本語メッセージを確認できる。上流APIの生レスポンスや内部情報は表示されない。

**Why this priority**: 現在の生のHTTPレスポンスや簡易メッセージだけでは、ユーザーが次に取るべき行動を判断できないため。

**Independent Test**: チャットの通常HTTPエラーとストリーミング中の安全なSSEエラーイベント、モデル一覧・会話一覧のHTTPエラーをステータス別にモックし、エラー種別に応じたメッセージと再試行操作が表示されることを確認できる。

**Acceptance Scenarios**:

1. **Given** APIが429を返した状態、**When** エラーが画面へ伝播する、**Then** 「リクエストが多すぎます。しばらく待ってから再試行してください。」と表示される
2. **Given** APIがタイムアウトまたは408/504を返した状態、**When** エラーが画面へ伝播する、**Then** 「応答に時間がかかりすぎました。再試行してください。」と表示される
3. **Given** APIが認証失敗または無効なAPIキーを示す401/403を返した状態、**When** エラーが画面へ伝播する、**Then** 「API キーが無効です。管理者にお問い合わせください。」と表示される
4. **Given** APIが上記以外の5xxまたはネットワーク/SSEエラーを返した状態、**When** エラーが画面へ伝播する、**Then** 技術的詳細を露出せず、再試行を促す一般的なエラー表示が出る
5. **Given** APIエラーのレスポンス本文にキー、スタックトレース、上流エラー本文が含まれる状態、**When** エラーを表示またはログ出力する、**Then** 機密情報と上流本文はユーザー向けUIと安全なログへ出力されない

### User Story 2 - エラーから再試行する (Priority: P2)

ユーザーはエラー表示から再試行でき、入力中のメッセージや現在の会話を失わずに処理を続けられる。

**Independent Test**: 失敗するAPIを一度返した後に成功するようモックし、再試行ボタンを押すと同じ操作が一度だけ再実行され、成功後にエラー表示が消えることを確認できる。

**Acceptance Scenarios**:

1. **Given** チャット送信がエラーになった状態、**When** ユーザーが再試行ボタンを押す、**Then** 同じ会話と入力内容でリクエストが1回だけ再実行される
2. **Given** モデル一覧または会話一覧の取得がエラーになった状態、**When** ユーザーが再試行ボタンを押す、**Then** 対象の取得処理だけが再実行される
3. **Given** 再試行が成功した状態、**When** 成功レスポンスを受信する、**Then** エラー表示が解除され、通常の画面またはストリーミング表示へ戻る
4. **Given** 再試行中の状態、**When** ユーザーが再試行ボタンを連打する、**Then** 同一処理の重複リクエストを送信しない

### User Story 3 - エラー後も会話を安全に継続する (Priority: P2)

ユーザーはエラー発生後も既存の会話履歴と入力内容を失わず、エラーの原因を確認してからチャットを継続できる。

**Independent Test**: 送信、エラー表示、再入力または再試行、成功送信の順に操作し、既存履歴の重複・欠落がなく、成功した応答だけが履歴に追加されることを確認できる。

**Acceptance Scenarios**:

1. **Given** APIエラーが発生した状態、**When** エラー表示が出る、**Then** 既存の会話履歴は消えず、ユーザー入力も意図せず失われない
2. **Given** エラー表示中にユーザーが新しいメッセージを入力した状態、**When** 新しい送信を行う、**Then** エラー状態が適切に解除され、新しい送信を開始できる
3. **Given** ストリーミング中に通信エラーが発生した状態、**When** エラー処理を行う、**Then** UIは生成中のままにならず、再試行または新規送信が可能になる

## Error Taxonomy

| 分類 | 判定例 | ユーザー向けメッセージ |
|------|--------|------------------------|
| Rate limit | HTTP 429 | リクエストが多すぎます。しばらく待ってから再試行してください。 |
| Timeout | 明示的なタイムアウト、HTTP 408、HTTP 504（ユーザー停止による`AbortError`を除く） | 応答に時間がかかりすぎました。再試行してください。 |
| Authentication | 上流APIの認証失敗、APIキー無効 | API キーが無効です。管理者にお問い合わせください。 |
| Session authentication | Functions APIの401（既存の認証トークン期限切れ） | 既存のログアウト・再ログインフローへ遷移する |
| Network / stream | fetch失敗、SSE読取失敗、レスポンスボディなし、分類不能なストリームエラー | 通信に失敗しました。接続を確認して再試行してください。 |
| Server / unknown | HTTP 5xx、分類不能なHTTPエラー | サーバーでエラーが発生しました。再試行してください。 |

## Requirements

### Functional Requirements

- **FR-001**: FrontendはAPIエラーをHTTPステータス、タイムアウト、ネットワーク、SSE、分類不能の種別へ正規化しなければならない
- **FR-002**: 429エラーにはレート制限用の日本語メッセージを表示しなければならない
- **FR-003**: タイムアウトにはタイムアウト用の日本語メッセージを表示しなければならない
- **FR-004**: 401/403またはAPIキー無効には認証設定を案内する日本語メッセージを表示しなければならない
- **FR-005**: ネットワーク、SSE、5xx、未知のエラーには内部詳細を隠した再試行可能なメッセージを表示しなければならない
- **FR-006**: エラー表示には対象操作を再実行できる再試行ボタンを提供しなければならない
- **FR-007**: 再試行中は同じ操作の重複リクエストを防がなければならない
- **FR-008**: チャット送信エラー時、ユーザーが入力した内容と会話コンテキストを意図せず破棄してはならない
- **FR-009**: エラー表示は成功、再試行、新規送信のいずれかで適切に解除されなければならない
- **FR-010**: エラー表示はスクリーンリーダーで通知されるよう、適切なstatusまたはalert semanticsを持たなければならない
- **FR-011**: APIキー、Authorizationヘッダー、スタックトレース、上流レスポンス本文、ユーザープロンプトをユーザー向けエラー表示へ含めてはならない
- **FR-012**: Backendはストリーミング中に発生した上流エラーを通常のアシスタント本文として送信・保存してはならず、安全なエラーコードを含むSSEエラーイベントとしてFrontendへ通知しなければならない
- **FR-013**: ストリーミング中のエラーイベントは、少なくとも`rate_limit`、`timeout`、`authentication`、`server`、`network`のいずれかの安定したコードを持ち、APIキー、上流エラー本文、スタックトレースを含めてはならない
- **FR-014**: チャットの再試行は、既に保存済みのユーザーメッセージを識別して再利用または冪等に処理し、同じユーザーメッセージを重複保存してはならない
- **FR-015**: ユーザー停止操作による`AbortError`はエラーとして分類せず、P1-003の中間保存フローへ委譲しなければならない
- **FR-016**: Functions APIの認証トークン期限切れによる401は、通常HTTPとチャットSSEの両経路でAPIキー無効のメッセージへ変換せず、既存のログアウト・再ログインフローへ遷移しなければならない

### Streaming Error Contract

ストリーミング中にBackendが送信するエラーイベントは、エラー分類に必要な最小限の情報だけを含める。

```text
data: {"error":{"code":"rate_limit"}}
```

Frontendは`code`をError Taxonomyのユーザー向けメッセージへ変換し、エラーイベント受信後にストリームをエラー終了する。Backendは上流の生レスポンス本文をイベントへ転記しない。

ユーザーの停止操作で発生した中断はこの契約のエラーイベントにせず、P1-003の停止・中間保存として扱う。

### Outbound API Behavior

- 自動リトライは本機能の必須要件とせず、ユーザー操作による再試行を基本とする
- 再試行は元の対象（チャット、モデル一覧、会話一覧など）だけを再実行する
- 再試行後も失敗した場合は、最新のエラー種別に応じた表示を維持する

## Success Criteria

### Measurable Outcomes

- **SC-001**: 通常HTTPエラーまたはストリームエラーイベントとして発生する429、タイムアウト、上流認証失敗、ネットワーク、5xxの各テストで、分類に応じた日本語メッセージが表示される
- **SC-002**: エラー発生後5秒以内に、エラー内容と再試行操作がユーザーへ表示される
- **SC-003**: 再試行ボタンの連打で重複リクエストが発生しない
- **SC-004**: エラー後の再試行成功でエラー表示が解除され、チャットを継続できる
- **SC-005**: エラー表示とテストログにAPIキー、Authorizationヘッダー、上流レスポンス本文が含まれない
- **SC-006**: FunctionsとFrontendのunit/integration test、buildが成功する

## Out of Scope

- OpenCode Go側の障害、レート制限、APIキーそのものの修正
- バックエンドの自動リトライ・キューイング・サーキットブレーカー。ただし、ストリーミング中の安全なエラーイベント伝達は本仕様に含む
- ストリーミング停止時の中間保存（P1-003）
- データ取得中のローディング画面・スケルトンデザイン（P2-013）
- エラーの詳細な管理者向け監視・アラート基盤

## Assumptions

- 現行のFrontend APIヘルパーと`useChat`などのhooksをエラー分類の境界として利用する
- Backendは通常のHTTPエラーについて既存のHTTPステータスを可能な範囲で維持し、Frontendでユーザー向け文言へ変換する
- ストリーミング中の上流エラーは、Backendが安全なエラーコードのSSEイベントへ変換する
- 認証有効時のFunctions APIのセッション期限切れ処理は既存のログイン遷移方針を維持し、APIキー無効の案内対象から除外する
- チャット再試行の重複防止に使うメッセージ識別子または冪等性キーの方式は実装計画で決定する
- 開発・テストではAPIレスポンスをモックし、通常テストから実APIを呼び出さない
